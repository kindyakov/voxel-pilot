# OpenAI Agents SDK: долгие действия харнеса

Проверено: 2026-09-19. Исследование для ADR-0005–0008 и черновика `../.scratch/new-ai-pilot-design.md`; не изменение согласованных решений. Проверены официальные JS docs и исходники `main`, не закреплённый npm-релиз. Код проекта, зависимости и сервер не запускались.

## Вывод

Рекомендуется инструмент **запуска действия**: вернуть подтверждённые харнесом `accepted` и идентификатор действия сразу после приёма. Продолжительная добыча принадлежит HSM. Завершение становится отдельным подтверждённым событием, которое приложение передаёт в следующий SDK-run того же разговора. Это адаптация предметного инструмента, а не самописная замена модельного цикла. Выбор «ответить / уточнить / пауза / заменить» остаётся за LLM; входящие сообщения не запускают кодовый классификатор намерений.

## Что предоставляется SDK

`run(agent, input, { session, stream: true, signal })` управляет вызовами модели и инструментов; `input` принимает строку или массив input items. SDK возвращает результат при финальном ответе без tools. Поэтому финальный ответ/вопрос не следует связывать с завершением игровой цели. Sessions обеспечивают продолжение разговора, не исполнение HSM. [Running agents](https://openai.github.io/openai-agents-js/guides/running-agents/).

Обычный function tool имеет `execute(args, context, details)`, может вернуть объект или Promise. `details.signal` доступен исполнителю; timeout тоже отменяет этот сигнал. SDK не может самостоятельно отменить Mineflayer: реакцию на сигнал обеспечивает адаптер. [Tools](https://openai.github.io/openai-agents-js/guides/tools/).

Для текста есть `toTextStream()`. Полный async event stream содержит `raw_model_stream_event` и `run_item_stream_event`, в том числе `tool_called`, `tool_output`, `message_output_created`. Это события tools/модели, не автоматически создаваемый игровой прогресс. Для прерывания передать и отменить `signal`; после этого всё равно дождаться `stream.completed`, включая сохранение и cleanup. `cancelled` и отсутствие `finalOutput` отличаются от нормального ответа. Продолжение незавершённого хода документировано через `stream.state` с той же session. [Streaming](https://openai.github.io/openai-agents-js/guides/streaming/).

## Вариант A: подтверждение запуска

Предлагаемая семантика: tool запрашивает действие у HSM и завершается результатом `{ actionId, status: 'accepted' }`, либо подтверждённым отказом. Пара tool call/result уже закрыта. Позднее `completed/failed/cancelled` — новое событие исполнения, а не второй результат того же tool call. Приложение передаёт его как явно обозначенный факт runtime через модельный вход/контекст; не подделывает реплику игрока. Точный формат input items и преобразование в RouterAI нужно проверить на выбранной версии.

SDK-native: tools, сериализация результата, следующий run и session. Ответственность проекта: подтверждение HSM, идентификаторы/дедупликация, доставка исходов, актуальность запуска, сохранение совершённых эффектов, порядок входящих сообщений. SDK не объявляет принятие действия его успешным исполнением; это определяется контрактом tool.

## Вариант B: ждать всю добычу внутри tool

Обычный SDK-loop ждёт результат tools перед следующим модельным решением. Чтобы ответить на новый вопрос во время ожидания, недостаточно записать сообщение в session: нужны прерывание/возобновление либо отдельный согласованный запуск. Отмена сетевого/SDK-run не должна автоматически отменять уже принятое игровое действие: это нарушит ADR-0005 для «сколько осталось?».

В исходнике streaming runner явно предусмотрено завершение текущего action batch перед запретом новой работы после отмены. Поэтому некооперативный долгий tool способен задержать освобождение разговора. Не следует обещать мгновенный переход на новое сообщение, просто вызвав abort. [Runner source](https://github.com/openai/openai-agents-js/blob/main/packages/agents-core/src/run.ts).

В актуальном `main` существует `RunState.addInput(input)`: добавляет вход перед следующей resumed model call. Он отклоняет terminal state, исчерпанный лимит ходов и некоторые состояния с уже принятым ответом, ожидающим обработки. Это полезная SDK-возможность для продолжения с поправкой, **не универсальная инъекция в работающий tool**. Наличие и поведение в выбранном опубликованном релизе ещё не проверены. [RunState source](https://github.com/openai/openai-agents-js/blob/main/packages/agents-core/src/runState.ts).

Вариант B технически возможен, но для постоянно доступного игрового диалога сложнее варианта A. Если SDK-run прекращён, а действие осталось работать, снова нужен отдельный контракт подтверждения и будущего результата.

## История и прерывания

Документация sessions различает сохранение: non-streaming пишет input и outputs после run; streaming пишет input сначала, outputs после завершения хода. Из этого нельзя выводить, что при любом abort все выполненные побочные эффекты уже сохранены в session. Полный журнал и реестр принятых операций нужны отдельно; восстановление не должно повторно запускать действие из-за потерянного SDK-output. Опциональный `SessionHistoryTransactionAwareSession` позволяет атомарные идемпотентные изменения истории с `operationId`, но не превращает внешнее игровое действие в транзакцию session. [Sessions](https://openai.github.io/openai-agents-js/guides/sessions/).

`callModelInputFilter` может менять и сохраняемые отфильтрованные items. Поэтому SDK-session нельзя без проверки считать неизменным полным журналом пользователя. Сжатый replay должен сохранять корректные связи вызовов и результатов; оборванный JSON/delta не является завершённым tool call. [Input filter](https://openai.github.io/openai-agents-js/guides/running-agents/#call-model-input-filter).

## Что проверить до реализации

Закрепить релиз и проверить в изоляции: отмену до tool, между приёмом HSM и возвратом результата, после результата и во время следующего запроса; запись session при каждом случае; `RunState.addInput` и его ограничения; отсутствие повторного старта принятого действия; допустимый replay через RouterAI Chat Completions. Отдельно определить, как новый run восстанавливает подтверждённые операции, если предыдущий stream не успел записать outputs. Эти гарантии пока не подтверждены тестами.
