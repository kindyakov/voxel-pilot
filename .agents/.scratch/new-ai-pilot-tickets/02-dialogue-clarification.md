## What to build

Игрок отправляет сообщение через Minecraft-адаптер общего интерфейса диалога; пилот отвечает, при необходимости осматривает мир и задаёт вопрос. Короткая следующая реплика продолжает тот же разговор. Сценарий демонстрируется в изолированной композиции нового пилота.

Покрытие пользовательских историй спецификации: 1–9,28,30,36. Все решения о поведении принимает LLM; код обеспечивает контракты и исполнение. Это черновик для согласования разбиения; T-номера обозначают будущие задачи, а не опубликованные Issues.

## Acceptance criteria

- [ ] Приём сообщения возвращает подтверждение; общий интерфейс предоставляет чтение разговора, исходящие реплики и события обработки.
- [ ] Модель может вызвать существующие инструменты осмотра и сформулировать уточнение на основании полученных фактов.
- [ ] Вопрос модели и финальный текст SDK-run не означают завершения игровой цели; ответ игрока не теряет обсуждаемые условия.
- [ ] Неоднозначность определяет LLM. Нет распознавания игровых фраз в коде и обязательного предварительного запроса-классификатора.
- [ ] В Minecraft передаются короткие смысловые реплики; общий интерфейс содержит текстовые фрагменты и события tools без SDK-типов и Minecraft-форматирования.
- [ ] Сохраняются существующий способ адресовать сообщение боту и исключение собственных сообщений бота.
- [ ] Основная проверка проходит через публичный интерфейс с управляемой моделью и внешними игровыми зависимостями; реальные решения LLM оцениваются отдельным прогоном.
- [ ] Для этого этапа разговор может храниться в процессе; долговечность реализуется отдельной зависимой задачей. Новый и старый пилоты не получают одни и те же входящие сообщения одновременно.
- [ ] Для изменённого кода выполнены проверка типов, сборка и релевантные изолированные тесты; обычная проверка не запускает живого бота.
