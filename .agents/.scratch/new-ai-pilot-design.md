# Новый пилот: сводный проект

Дата: 2026-09-19. Статус: сводка согласованных архитектурных решений и техническое предложение по их реализации; код и зависимости не изменены. Совместимость SDK с RouterAI, восстановление прерванного запуска и достижимость целевой задержки ещё не проверены экспериментально.

## Согласованные решения

- [ADR-0005](../adr/0005-pilot-dialogue-and-execution.md): диалог отделён от исполнения; неоднозначность и смысл свободного текста определяет LLM.
- [ADR-0006](../adr/0006-openai-agents-sdk-pilot.md): OpenAI Agents SDK, RouterAI, сменяемые модели.
- [ADR-0007](../adr/0007-channel-independent-dialogue.md): единый разговор между каналами, события текста, инструментов и прогресса. Сейчас реализуется только Minecraft-адаптер; GUI и его сетевой транспорт вне задачи.
- [ADR-0008](../adr/0008-dialogue-history-and-model-context.md): полный журнал для пользователя, ограниченный контекст модели, проверяемое состояние исполнения отдельно от сводки.
- [ADR-0009](../adr/0009-long-action-acceptance-and-result.md): подтверждение запуска длительного действия и отдельная доставка его результата.

Далее предложена конкретизация этих решений. Она не утверждает, что текущий код уже реализует данный контракт.

## Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| Диалог пилота | Приём сообщений, порядок обработки, активный запуск модели, сбор контекста и выдача событий |
| Интеграция Agents SDK | Инструкции, tools, модельный цикл, перевод SDK-событий в события проекта |
| Хранилище разговора | Сообщения, завершённые результаты инструментов, сведения о прерывании и сводка старого контекста |
| Связь пилота с харнесом | Типизированные запросы действий, приём подтверждений, прогресса и исходов |
| Харнес | Единственное исполнение игровых действий, отмена, выживание, самооборона и владение ресурсами |
| Minecraft-адаптер | Приём адресованных боту сообщений, форматирование и доставка коротких реплик |

SDK не вызывается из адаптера чата. Пилот не получает прямое управление движением. Хранение агентских данных интегрируется с существующими владельцами персистентности, без самостоятельных файловых записей из tools.

## Предлагаемый интерфейс диалога

Операции: принять сообщение; прочитать историю и текущее состояние; подписаться на события; отправить явную команду управления. Интерфейс не зависит от HTTP, WebSocket или SDK-типов.

Предлагаемая поверхность интерфейса:

| Операция | Результат и обязательства |
| --- | --- |
| `submitMessage` | Сохраняет сообщение и возвращает подтверждение приёма с его идентификатором, не ожидая ответа LLM. Ошибка сохранения не выдаётся за успешный приём. |
| `readConversation` | Возвращает страницу истории и согласованное состояние разговора, текущей обработки и исполнения с курсором событий. |
| `watchConversation` | Продолжает чтение событий после курсора. Если продолжить без потерь нельзя, явно требует повторного чтения состояния. |
| `control` | Принимает явное управление: отменить указанный ответ модели или остановить текущую игровую цель. Эти операции имеют разные последствия и не выводятся из текста программным классификатором. |

Названия предварительные. Курсор относится к порядку событий разговора, а не к времени на часах клиента. Результат приёма пользовательского сообщения, завершённый ответ модели и успешное выполнение игровой цели различаются и в данных, и в пользовательских уведомлениях.

Сообщение содержит идентификаторы разговора, сообщения и отправителя, текст и сведения о канале доставки. Повторная доставка того же сообщения не должна повторно запускать поручение. Канал не является идентификатором разговора.

Идентификатор разговора связывает историю между каналами; идентификатор сообщения позволяет распознать повтор доставки; идентификатор запуска отделяет актуальный ответ от отменённого; идентификатор действия связывает запрос с подтверждённым прогрессом и результатом харнеса. Подключение клиента само по себе не создаёт цель и не запускает модель.

События различают:

- приём сообщения и состояние обработки моделью;
- фрагмент текста и завершённую реплику;
- запрос инструмента, результат или ошибку инструмента;
- принятие игрового действия, прогресс и конечный исход;
- прерывание ответа, ожидание пользователя и недоступность пилота.

Каждое событие относится к конкретному разговору и запуску; игровые события дополнительно связаны с действием и целью. Нужен порядок событий внутри разговора. При повторном подключении клиент сначала восстанавливает состояние и историю, затем продолжает подписку без пропусков. Механизм курсора и срок хранения событий уточняются при реализации интерфейса; не обязательно хранить каждый текстовый фрагмент как постоянную запись.

## Долгие действия и новые сообщения

Длительное игровое действие запускается через харнес с немедленным подтверждением приёма и идентификатором действия. Конечный результат приходит отдельным событием. Принятие действия не означает его успеха. Так модельный запуск не обязан ждать всю добычу, а разговор может продолжаться во время работы.

Инструмент запуска возвращает подтверждённые `accepted` и `actionId` либо отказ. Поздний исход действия передаётся как новый явно обозначенный факт runtime того же разговора, а не как второй output уже завершённого tool call и не как реплика игрока. Модель по этому факту выбирает дальнейшее поведение. Прогресс обновляет состояние и поток событий без обязательного модельного запроса на каждый апдейт.

Альтернатива — ждать всю добычу внутри tool — удерживает SDK-run в ожидании и усложняет обработку новых сообщений. Поэтому принято короткое подтверждение запуска. Проверка SDK и ограничения опубликованного API описаны в [исследовании долгих действий](../research/agents-sdk-long-actions.md).

Результаты инструментов осмотра доступны внутри обычного SDK-loop. Завершение игрового действия поступает пилоту как подтверждённый факт для следующего решения. Каждый блок добычи не требует отдельного вызова LLM; сводный прогресс доступен для ответа игроку. Это адаптация предметного исполнения к готовому SDK-loop, а не второй самописный модельный цикл.

Внутри разговора предлагается один активный запуск модели. Новое сообщение сохраняется, инвалидирует старый запуск и инициирует обработку накопленных сообщений с актуальным состоянием. Все поступившие сообщения сохраняются, а не заменяются последним.

При остановке SDK-stream необходимо дождаться его завершения и завершения записи истории до начала нового запуска с той же session. Встроенное возобновление SDK применяется там, где выбранный релиз поддерживает добавление актуального входа в соответствующее состояние. Возможность `RunState.addInput`, найденная только в `main`, не считается гарантией опубликованного релиза. При новой обработке уже исполненные операции сверяются с подтверждёнными результатами, а не запускаются повторно из старого состояния.

Проверка актуальности запуска выполняется до принятия операции с побочным эффектом. Поздний ответ старого запуска не может начать новое действие. Операция, уже принятая харнесом, не исчезает вместе с отменённым ответом модели: её исход сохраняется и учитывается новым запуском. Аналогично нельзя терять выполненную запись памяти или повторять её только потому, что прервался ответ модели.

Отмена генерации и отмена игровой цели — разные операции. Существующая явная остановка цели не требует ожидания LLM; она не отменяет обязанности выживания. Свободный текст сначала интерпретируется моделью.

LLM выбирает, ответить ли, задать вопрос, продолжить, приостановить или заменить действие. Сам вопрос модели не останавливает харнес. Для изменения исполнения нужен соответствующий выбранный моделью инструмент. Код проверяет его аргументы, актуальность запуска и допустимость операции; обязательной поведенческой цепочки для неоднозначной поправки нет.

## История и контекст

Журнал сохраняет сообщения и подтверждённые результаты. Незавершённые операции после сбоя не выдаются за успешные. Адаптер SDK формирует допустимую последовательность сообщений и результатов tools; прерванный вызов не должен оставлять в следующем запросе некорректную пару вызов/результат.

Полный журнал пользователя не отождествляется с SDK-session без проверки её семантики: streaming сохраняет вход раньше выходов, а фильтрация модельного контекста может влиять на сохраняемые items. Сжатие и прерывание не должны лишать приложение сведений о принятых харнесом действиях.

Контекст модели собирается из инструкций, актуальной цели и исполнения, последних реплик, сводки старого разговора и необходимых результатов инструментов. Сводка имеет определённую границу охваченной истории; новые сообщения не должны теряться при её обновлении. Неудача сжатия не разрешает удалять журнал или отправлять запрос сверх лимита контекста.

После рестарта восстанавливаются разговор и ожидаемое уточнение. Игровая цель не запускается автоматически; действуют существующие правила сохранённых задач. История не считается свежим наблюдением мира.

## Проверяемые сценарии

1. «Добудь дерево» → осмотр → уточнение вида и количества → «10 дуба» → сообщение о плане → действие. До уточнения добыча не начинается.
2. «Вскопай 5 песка» → запуск одного поручения → подтверждённые пять новых предметов → результат, без повторного заказа той же добычи.
3. Во время добычи «сколько осталось?» получает ответ из актуального состояния без отмены добычи.
4. Новое сообщение во время запроса модели учитывается новым запуском; запоздалое решение старого не начинает действие.
5. При прерывании в момент принятия действия сохраняется ровно факт принятого действия и его исход; новое решение не дублирует работу.
6. После рестарта доступна история, но бот не начинает добывать самостоятельно.
7. Другой тестовый адаптер получает тот же разговор и структурированные события без Minecraft-зависимостей; GUI для этой проверки не нужен.
8. Сжатие не меняет исходный журнал, цель и подтверждённый прогресс.
9. Невалидные аргументы, транспортный сбой, отмена и остановка не превращаются в успешное завершение. Проверяются также найденные при ревью ошибки JSON parsing, фильтра удаления памяти и вложенных retries.

Диалоговые примеры проверяют качество поведения LLM и инструкций, а не задают правила распознавания фраз в коде. В изолированных тестах проверяется исполнение явно выбранных операций: вопрос без инструмента паузы не останавливает действие; валидный инструмент паузы исполняется харнесом. Нужна также отдельная оценка поведения реальной модели на неоднозначных поручениях.

## Скорость и порядок реализации

Целевой сценарий — до двух секунд от приёма понятного поручения до начала исполнения в нормальных игровых условиях. Время до первого текста, готового tool call, приёма действия харнесом и фактического начала измеряется раздельно. Поиск для уточнения и ожидание игрока не маскируются быстрым подтверждением получения.

Сначала проверить выбранные версии SDK и протокол RouterAI в изолированном сценарии с тестовыми tools. Сравнить поддерживаемые настройки reasoning на одной модели и одинаковых входах; считать число обращений, задержки и корректность поведения. Настройки модели не следует угадывать по совместимому формату API. Живое подключение к Minecraft для этой проверки не требуется.

Затем реализовать интерфейс диалога, хранение и изолированные проверки; подключить SDK; интегрировать приём и исходы действий харнеса; подключить Minecraft-адаптер. Старый и новый пилоты не должны одновременно управлять ботом. После переключения удалить заменённый цикл и обновить карту архитектуры.

При изменении кода обязательны type-check, build и релевантные изолированные тесты. Live-проверка выполняется только в согласованном окружении и отдельно подтверждает время физического начала действия.
