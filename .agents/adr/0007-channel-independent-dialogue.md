# Общий интерфейс диалога для Minecraft-чата и будущего GUI

Статус: принято для проектирования; реализация ещё не изменена
Согласовано: 2026-09-19

После v1 планируется GUI со встроенным чатом пилота. Уже при проектировании нового пилота выделяем независимый от канала интерфейс диалога. Minecraft-чат подключается через адаптер; будущий GUI и другие клиенты используют тот же модуль диалога.

## Решение и границы

Логика разговора, интерпретация сообщений, история и взаимодействие с харнесом принадлежат модулю пилота, а не адаптерам каналов. Внешний интерфейс выражает сообщения и состояние работы в понятиях проекта; типы OpenAI Agents SDK остаются деталями реализации. Ограничения длины, форматирование и способ доставки Minecraft-сообщений принадлежат его адаптеру.

- Разговор продолжается между каналами: открытие будущего GUI не создаёт отдельную историю для уже существующего разговора. Канал доставки и разговор — разные понятия.
- Интерфейс предоставляет поток текста ответа, события вызовов инструментов и прогресс игровых действий. Адаптер Minecraft-чата показывает короткие смысловые сообщения; будущий GUI сможет представлять эти же события подробнее. Вывод скрытых рассуждений не является требованием.
- Новое сообщение во время незавершённого ответа модели прерывает устаревающий запуск; пилот продолжает обработку с новым сообщением в контексте. Поздние решения старого запуска не вправе начинать действия. Отмена ответа модели сама по себе не отменяет уже запущенное игровое действие и не откатывает совершённые эффекты.
- Текущая область работ — интерфейс пилота и Minecraft-адаптер. GUI-приложение, его экраны и сетевой транспорт для него сейчас не разрабатываются.

## Компромисс

Общий контракт требует явного проектирования входящих сообщений, чтения истории и событий работы вместо прямой связки модель → `bot.chat`. Это позволяет добавлять клиенты без копирования поведения пилота. Альтернатива — формировать весь диалог непосредственно в Minecraft-чате — заставила бы переносить или дублировать его при создании GUI.

Решение не выбирает HTTP, WebSocket, SSE или локальный IPC. Идентификаторы сообщений и запусков, порядок событий, восстановление подписки и сохранение результатов уже совершённых операций при прерывании требуют детального проектирования. Эти механизмы не должны перекладывать управление пилотом на клиентов.
