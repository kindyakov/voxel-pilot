# Диалог пилота отделён от исполнения цели

Статус: принято для проектирования; реализация ещё не изменена
Согласовано: 2026-09-18

Текущий цикл связывает текстовый ответ модели с завершением цели, а новое сообщение игрока — с заменой поручения. Это мешает уточнять цель и отвечать игроку во время исполнения. Перепроектируем пилот и его связь с игровым чатом, сохраняя харнес, игровые исполнители и проверки допустимости действий. Основа нового пилота — OpenAI Agents SDK ([ADR-0006](0006-openai-agents-sdk-pilot.md)).

## Решение

- Диалог продолжается независимо от длительности действия. Завершение ответа модели, ожидание уточнения и завершение игровой цели имеют разные значения.
- Неоднозначность поручения и смысл последующих сообщений определяет LLM по инструкциям и контексту. Для предметного уточнения пилот может сначала получить факты инструментами осмотра: например, найти доступные виды дерева перед вопросом игроку. Ответ игрока дополняет обсуждаемое поручение.
- LLM выбирает реакцию на сообщение: ответить, уточнить, продолжить действие, приостановить его или заменить поручение. Вопрос о ходе работы не должен сам по себе прерывать исполнение. Нет обязательного правила «неоднозначная поправка → уточнение → пауза»: необходимость вопроса и операции управления определяет модель по контексту. Код обеспечивает сохранение состояния, проверку инструментов и корректное исполнение выбранных операций, без распознавания отдельных игровых фраз специальными ветками.
- Новое текстовое сообщение сначала рассматривает LLM с контекстом диалога и исполнения. Само поступление сообщения не является основанием останавливать действие или заменять цель. Явные команды управления, например существующая `:stop`, отличаются от интерпретации свободного текста.
- История диалога, включая незавершённое уточнение, сохраняется после перезапуска. Восстановление истории не запускает игровые действия автоматически; актуальные факты о мире проверяются заново.
- Полный журнал разговора отделён от ограниченного контекста модели. Старые сообщения можно сжимать в сводку для LLM; цель, прогресс и результаты действий остаются отдельными проверяемыми данными ([ADR-0008](0008-dialogue-history-and-model-context.md)).
- Пилот сообщает о принятом плане, существенном прогрессе, смене плана, препятствии и результате; отдельный вызов инструмента не требует отдельной реплики в Minecraft-чате. На вопрос о ходе работы отвечает с учётом текущего состояния исполнения.
- Харнес остаётся единственным владельцем исполнения, движения, выживания и отмены. Сохраняются границы [ADR-0003](0003-autonomy-without-ai.md) и правила персистентных записей из [ADR-0004](0004-persistent-task-records.md).
- Длительные инструменты возвращают подтверждение запуска; прогресс и конечный исход приходят отдельно от харнеса ([ADR-0009](0009-long-action-acceptance-and-result.md)).
- Используем существующий игровой чат. Многопользовательскую маршрутизацию в эту область работ не добавляем. Сохраняем подключение через RouterAI с OpenAI-совместимым API и возможностью смены модели.
- Интерфейс диалога должен поддерживать будущий GUI и другие каналы без переноса логики пилота в клиенты ([ADR-0007](0007-channel-independent-dialogue.md)).

## Компромисс и открытые вопросы

Одного изменения системного промпта недостаточно: приложение должно поддерживать продолжение диалога и сообщения во время работы харнеса. При этом второй исполнитель игровых действий не появляется. Схема связи пилота с харнесом принята в ADR-0009; конкретные типы, обработка конкурирующих событий и формат хранения требуют технической проверки при реализации. Само уточнение не запускает кодовую политику паузы, продолжения или таймера ожидания: реакцию на свободный текст выбирает LLM. Это не отменяет независимые правила выживания, валидацию инструментов и явные команды управления.

Это решение меняет будущий контракт управления пилотом. Текущий маршрут `THINKING → EXECUTING → DECIDE_NEXT`, описанный в `ARCHITECTURE.md`, остаётся картой существующей реализации до согласования конкретной схемы и её внедрения. Двухсекундный старт понятного поручения — целевое требование, достижимость которого нужно проверить на выбранных модели и провайдере.
