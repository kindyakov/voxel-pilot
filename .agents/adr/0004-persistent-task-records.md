# Персистентные записи задач: переживают рестарт как suspended, исполняет HSM

Статус: принято
Согласовано: 2026-09-17
Заменяет: — (новое решение)

## Контекст

In-memory прогресс добычи (Фаза 1, `src/hsm/tasks/task.ts`) переживает вытеснение
боем/выживанием/наблюдением, но умирает вместе с процессом. Нужны задачи,
переживающие перезагрузку бота, видимые пилоту (список/создание/запуск/отмена),
без второго исполнителя и без шедулера: активная цель по-прежнему одна,
владелец исполнения — HSM, планировщик — `THINKING/DECIDE_NEXT + goalExecution`.

## Решение

1. **Владелец — `MemoryManager`**: новая таблица `bot_tasks`
   `(id, kind, status, block_name, total, done, created_at, updated_at)`,
   формат `tasks_format_version = 1` в `memory_meta`. Статус:
   `suspended | active | completed | failed | cancelled`.
   Невалидные строки не роняют чтение: неизвестный статус → `suspended`,
   битый `done` → `0`, битый `total`/`block_name` → строка отбрасывается.
2. **Минимум полей (Q13.1a)**: `{ id, kind: 'mining', blockName, total, done,
status, createdAt, updatedAt }`. Позиции поиска, блеклист, попытки —
   runtime-состояние, при resume перестраиваются поиском.
3. **Без автозапуска (Q13.2a)**: на старте `normalizeTasksOnBoot` переводит
   `active → suspended` (краш mid-run), прогресс `done` сохраняется.
   Машина стартует как раньше; resume — только явным `tasks_start` или
   командой игрока.
4. **Инструменты пилота (Q13.3)**: `tasks_list` — inline (только чтение);
   `tasks_create` / `tasks_start` / `tasks_cancel` — execution через HSM
   (`RESOLVE → TASK_CREATE/TASK_START/TASK_CANCEL`), мутации стора только
   из экшенов машины. Пилот мимо харнеса ничего не пишет.
5. **Связь с runtime**: `MiningTask.taskId`. `MINING` входит только со
   связанной записью: ошибка линковки маркирует задачу (`lastFailure`,
   без `taskId`) и уходит в `TASK_FAILED` до первого копания —
   несвязанного исполнения нет. `tasks_start` поднимает `suspended`-запись
   в `MINING` с `collected = done`, минуя `THINKING` (как resume Фазы 1).
6. **Синхронизация отказов**: успех (`TASK_COMPLETED`) выдаётся только через
   `TASK_SYNCING` после успешной terminal-записи, причём проверяется и
   возвращённая строка (null/чужой id/статус/`done` = провал).
   Отсутствующий `taskId`/стор тоже валит gate (fail-closed): успех без
   записи невозможен даже при потере prerequisite. Провал записи ведёт
   в выделенный `TASK_SYNC_FAILED` (вердикт FAILED с причиной), а не
   в общий `TASK_FAILED`: запись остаётся `active` с последним
   подтверждённым `done`, без ложного успеха и без терминального
   клейма. `done` после каждого `BROKEN` — fire-and-forget: `done`
   абсолютен, пропуск самовосстанавливается следующей записью, а вердикт
   сторожит gate. Ошибка записи в ветке `TASK_FAILED` не меняет уже
   честный провал, только логируется. Все мутации сверяют эхо стора
   (id/status/payload); несовпадение — отказ операции, не молчание.
7. **Осиротевшие active-записи**: `active` без runtime-владельца (след
   sync-провала) не кирпич: `tasks_start` усыновляет такую запись
   (adopt с `done`), `tasks_cancel` отпускает её. Boot-нормализация
   остаётся вторым рубежом.
8. **Каждый `mine_resource` пишет строку** (история + crash recovery).
   Чистка старых терминальных строк — будущая работа, не этот ADR.

## Отброшенные альтернативы

- **Отдельный task-worker/шедулер с очередью**: второй исполнитель рядом с HSM,
  дублирование владения движением и бюджета. Отброшено; очередь некому
  пополнять при одной активной цели.
- **Хранение прогресса в `memory_entries` тегами**: записи привязаны
  к позиции `(type,x,y,z)` и upsert-семантике — чужая семантика для очереди
  задач. Отдельная таблица честнее.
- **Полный снапшот runtime-задачи** (позиции, блеклист): протухает за время
  дауна; resume обязан переискать мир. Отброшено.
- **Автопродолжение после рестарта**: бот сам уходит копать без команды.
  Небезопасно, запрещено контрактом без отдельного решения. Отброшено.

## Компромисс

Рост таблицы от каждого `mine_resource` без чистки. Принято сознательно:
история нужна для `tasks_list`, чистка — дешёвая отдельная задача, когда
появится второй вид задач.
