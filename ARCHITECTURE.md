# Инструкции по архитектуре для AI-агентов

Используй этот файл при анализе кода, ревью, диагностике и реализации: здесь определены карта, владельцы поведения и правила расширения. Порядок работы и роли источников заданы в [AGENTS.md](AGENTS.md). Это внутренние инструкции для агентов, не публичный обзор проекта.

## Границы workspaces

`packages/contracts` владеет переносимыми интерфейсами и DTO: обычные сериализуемые данные, без Node.js, Mineflayer, XState и UI-фреймворков. `packages/core` использует contracts и владеет поведением, Mineflayer-адаптерами и тестами подсистем. `apps/cli` владеет процессом, сигналами и самостоятельными командами. Приложение импортирует только публичные ESM exports workspaces; внутренний алиас `@/*` действует внутри ядра. Межпакетные зависимости объявляй через `workspace:*`; прямые runtime- и type/test-зависимости размещай у потребителя. Границы и объявления проверяет `pnpm run check:imports`.

Публичные exports ядра безопасны при импорте без окружения и пользовательских файлов. Конструирование `MinecraftBot(services, connectionOverrides?)` захватывает явные сервисы и адаптеры; подключение и открытие хранилищ выполняет только `start()`. Конфигурация — валидируемый неизменяемый снимок, logger принадлежит создавшему его приложению и закрывается после остановки runtime. [bootstrap.ts](apps/cli/src/bootstrap.ts) выбирает пути и вывод; [settings.ts](apps/cli/src/settings.ts) явно читает выбранный файл и объединяет его с переданным окружением, где заданные значения окружения имеют приоритет. Default пути `.env`, `data/`, `logs/` принадлежат корню репозитория и вычисляются в [runtimePaths.ts](packages/core/src/runtimePaths.ts), одинаково для src/dist и рабочего каталога CLI. Изменения пути не меняют формат или владельца памяти. Viewer и web inventory сохраняют отсутствие автоматического запуска.

Приложения получают от `createBotRuntime` замороженный фасад `BotRuntime` из contracts: start, stop и telemetry. [runtime.ts](packages/core/src/core/runtime.ts) владеет полным неизменяемым кешированным снимком и конечным дедлайном остановки; subscribe сразу доставляет текущий снимок и возвращает disposer. Ошибки и reentrant-вызовы подписчиков изолированы. Измерения остаются явно неизвестными до реализации наблюдения их источников. Native `MinecraftBot` сохраняется как нижний интерфейс композиции и совместимости; UI использует переносимый фасад.

Root-команды делегируют сборку и проверки пакетам. `type-check` сначала собирает пакеты в порядке зависимостей, затем проверяет их и root-тесты; потребители читают declarations через package exports. Все существующие регрессии запускаются `pnpm test` последовательно между файлами, чтобы тесты реальной физики не делили CPU slice. Самостоятельные команды находятся в `apps/cli/src/commands/`.

Для разработки `apps/cli` включает condition `development` публичных exports ядра и наблюдение за его исходниками; обычный Node.js использует собранные `dist` и declarations. Standalone-команды сначала собирают ядро. Относительные аргументы schematic-команды отсчитываются от каталога вызова pnpm (`INIT_CWD`), а генерируемая диаграмма остаётся в корневом `docs/diagrams/`.

## Правила новых файлов и интерфейсов

- При обновлении плагинов, изменении отмены контроллеров или процесса установки прочитай [patches/README.md](patches/README.md): патчи зависимостей — часть runtime-контракта передачи управления.
- Сначала расширяй существующий модуль-владелец. Создавай новый модуль, когда у поведения есть отдельный контракт или жизненный цикл; не создавай параллельные `services/`, `managers/` или `helpers/` без определённой ответственности.
- Держи `packages/core/src/ai/loop.ts`, `packages/core/src/ai/tools.ts` и `packages/core/src/ai/client.ts` тонкими публичными фасадами. Реализация живёт в одноимённых каталогах. Внешним потребителям предоставляй нужный контракт, а не всю внутреннюю структуру.
- Локальные типы оставляй рядом с реализацией. Контракты AI/HSM размещай в `packages/core/src/ai/contracts/`, события машины — в `packages/core/src/hsm/types.ts`, её данные — в `packages/core/src/hsm/context.ts`. В `packages/core/src/types/` выноси только действительно общие типы и декларации внешних библиотек.
- Именуй файл по ответственности: `*.guards.ts`, `*.actions.ts`, `*.actors.ts`, `*.primitive.ts`. Для остальных файлов следуй соседнему модулю: функции — camelCase, классы — PascalCase, фабрики — `create…`, события — `UPPER_SNAKE_CASE`.
- Используй TypeScript, явные контракты на границах и проверку внешних данных. Новый `any` или приведение типа не должны заменять валидацию либо скрывать несовместимость интерфейсов. Существующие широкие типы не являются шаблоном для нового кода.
- [Bot](packages/core/src/types/index.ts) расширяет настоящий тип Mineflayer только сервисами приложения. Дополнительные события объявляй в `BotEvents` через [module augmentation](packages/core/src/types/external/mineflayer.d.ts); ambient-декларация без импорта исходного модуля подменяет его API вместо расширения.
- Настройки форматирования и импортов бери из [.prettierrc](.prettierrc), алиасы и строгость — из [tsconfig.json](tsconfig.json). Между модулями используй существующие алиасы; внутри модуля допустимы короткие относительные импорты. Локальные импорты всегда пиши с явным расширением `.js` (директорию раскрывай до `/index.js`): `dist/` — чистый ESM, и `pnpm start` без расширений не резолвится. При изменении алиасов согласуй [knip.json](knip.json).
- Тест нового поведения размещай в соответствующей подсистеме `packages/core/src/tests/` как `*.test.ts`. Используй `node:test` и `node:assert/strict`; тестируй контракт через доступную точку входа.
- Runtime-код размещай в `packages/core/src/`. `dist/` — результат сборки, `data/` и `logs/` — runtime-данные. Назначение `docs/` и правила публикации определены в `AGENTS.md`.

## Границы поведения, которые нужно сохранять

### Жизненный цикл подключения

- [bot.ts](packages/core/src/core/bot.ts) владеет одной сессией подключения: HSM, чат-подписками, автосохранением и реконнектом. Disconnect и явная остановка сначала снимают право старой сессии управлять ботом; новое подключение ожидает завершения сохранения готовой старой сессии. Явная остановка отменяет реконнект.
- Подключение публикует собственные connecting/ready/reconnecting/failed факты. Ready означает готовность текущего харнеса после загрузки хранилищ. Исчерпание существующего бюджета реконнекта — терминальный отказ; [application.ts](apps/cli/src/application.ts) сводит его и сигналы к одному завершению с ненулевым исходом при отказе. Дедлайн приложения ограничивает и остановку runtime, и закрытие принадлежащего приложению logger.
- [harness.ts](packages/core/src/core/harness.ts) владеет загрузкой, сохранением и закрытием захваченных хранилищ памяти/профиля. `ready` сообщает успешный старт или отмену; `stop()` синхронно отменяет акторов, подписки и таймеры до ожидания persistence. Запоздалая загрузка после отмены может только закрыть свои ресурсы. Начальный контекст читает текущие показатели бота после загрузки памяти.
- Отмена и фактическое завершение ресурсов различаются. Native stop до готовности сохраняет немедленный результат; отдельный finalize ожидает уже начатые загрузки и позднее закрытие. Реконнект и новый start ожидают это завершение. Публичный stop возвращает сериализуемый отчёт об обязательном сохранении/очистке либо дедлайне с возможным неполным сохранением; поздний результат освобождает свои ресурсы и не меняет уже выданный исход. Ошибки собирает выполняющий операцию владелец, сырые причины остаются в диагностических логах.
- [initConnection](packages/core/src/modules/connection/runtimeConnection.ts) и `CommandHandler` освобождают собственные подписки через явный disposer; очистка одной зависимости не должна блокировать освобождение остальных.

### AI и исполнение

- LLM выбирает одно следующее действие, HSM владеет его исполнением. Цикл исполнения цели: `THINKING → EXECUTING → DECIDE_NEXT`. Новую возможность добавляй через контракт инструмента и исполнитель, а не через специальную ветку для конкретной фразы пользователя.
- Добыча: пилот передаёт конкретные `block_name` и `resource_name`, уточняя неоднозначность у игрока. [miningResource.ts](packages/core/src/hsm/tasks/miningResource.ts) связывает источник с предметом; [miningTool.ts](packages/core/src/utils/minecraft/miningTool.ts) выбирает harvest-инструмент с нужным Silk Touch. [task.ts](packages/core/src/hsm/tasks/task.ts) владеет пакетной очередью и чистым приростом инвентаря. [miningInventory.actors.ts](packages/core/src/hsm/actors/miningInventory.actors.ts) наблюдает только во время MINING; HSM завершает действие по полученным предметам. При resume сохраняется подтверждённый прогресс, baseline инвентаря начинается заново. Перед подходом и после экипировки проверяется актуальность цели; новый поиск выполняется после исчерпания очереди. Совместимость старых записей без явного ресурса проверяй в [MemoryManager.test.ts](packages/core/src/tests/core/memory/MemoryManager.test.ts).
- `snapshot` содержит минимальное состояние цикла. Факты об инвентаре, блоках, сущностях и содержимом окна получай через inspect-инструменты; долговечные факты — через memory API. Не подменяй grounding расширением снимка или текстовым обещанием в prompt.
- Для действия с объектом мира проверяй grounding в текущем ходе через [grounding.ts](packages/core/src/ai/loop/grounding.ts) и [validation.ts](packages/core/src/ai/loop/validation.ts). Исключения делай явными: `mine_resource` сам ищет ресурс; операции переноса и закрытия используют активную оконную сессию.
- Проверяй ответ модели до побочных эффектов: execution/control допускается только единственным вызовом в ответе. Невалидные аргументы дают `rejected`; HSM передаёт причину следующему ходу через `DECIDE_NEXT`, пока позволяет бюджет цели. Нетранспортный `failed` расходует бюджет отказов и завершает цель по действующему пути остановки. `isTransport: true` на границе хода отображается в `transport_failed`: он не расходует бюджет и не вправе вызывать `clearGoal`. Отмена распространяется отдельно, не ставит цель на паузу и не возвращает действующее решение.
- Execution-схема, parser, имя и summary сосредоточены в [executionDefinitions.ts](packages/core/src/ai/tools/executionDefinitions.ts); `PendingExecution` выводится из определений. HSM получает типизированный вариант, а примитив проверяет актуальный мир. Значения по умолчанию применяются только к отсутствующим опциям; `null`, неверный тип и лишние поля отклоняются.
- Каталог отправляется с `strict: false`: обязательные nullable-поля провайдерского strict-режима меняют контракт отсутствующих опций. Локальная проверка execution остаётся строгой и не преобразует данные. При смене режима сохраняй эту семантику и проверяй совместимость схемы с провайдером.
- [goalExecution.ts](packages/core/src/ai/goalExecution.ts) учитывает начатые действия и последовательные нетранспортные отказы. Успех сбрасывает серию отказов, но не общий расход; прерывание и `transport_failed` сохраняют оба счётчика. Новая цель начинает новый бюджет. Проверяй лимит также при возвращении из боя/выживания. Транспортные повторы принадлежат [retry.ts](packages/core/src/ai/client/retry.ts), а не этой политике.
- При транспортной недоступности пилота HSM переносит `currentGoal` в `pausedGoal` и остаётся в `IDLE`, сохраняя автономное выживание. Пока пилот включён, таймер `IDLE` возобновляет такую цель через `RESUMING → TASKS.THINKING`; повторный транспортный отказ снова ставит её на паузу без расхода бюджета. `pausedGoal` переживает реконнект. `STOP_CURRENT_GOAL` очищает его, а новая `USER_COMMAND` намеренно заменяет приостановленную цель.
- Провайдеры `disabled` и `local` используют [NoOpAgentClient](packages/core/src/ai/client/noOpClient.ts): он не создаёт сеть и сообщает машинно-читаемую недоступность пилота. Владелец проверки этих провайдеров и общего пользовательского сообщения — [pilotAvailability.ts](packages/core/src/ai/pilotAvailability.ts); фабрика клиента, обработчик команд и lifecycle бота используют один контракт.

### HSM и ресурсы

- При анализе или изменении машины, акторов и переходов используй проектный навык [xstate](.agents/skills/xstate/SKILL.md).
- [dependencies.ts](packages/core/src/hsm/dependencies.ts) задаёт захваченные logger, runner и настройки харнеса. Передавай их в фабрику машины и владельца сессии; размещай зависимости вне сериализуемого контекста и полей Mineflayer Bot. Конфигурацию окружения и политику вывода выбирает приложение. Проверка импортов запрещает в production core чтение `process.env`, загрузчик dotenv и зависимости от приложений/интерфейса.
- Машина определяет переходы, приоритеты и владельца движения. Акторы выполняют побочные эффекты. Новые guards должны проверять условия без запуска действий или скрытых повторов.
- Декоративным взглядом владеет [idleGaze.actors.ts](packages/core/src/hsm/actors/idleGaze.actors.ts), вызываемый только в `MAIN_ACTIVITY.IDLE` для живого бота со свежим наблюдением. Он выбирает видимых игроков и подтверждённо мирных мобов, исключая эндерменов и неживые сущности. Выход из состояния прекращает его обновления без восстановления старых углов; `movementOwner: NONE` не разрешает фоновый взгляд, поскольку стрельба тоже использует его. Ошибка взгляда останавливает только этот актор до следующего входа в `IDLE`.
- Перед изменением выбора цели, оружия, голода или причин отхода прочитай [ADR-0002](.agents/adr/0002-combat-without-default-retreat.md): он заменяет прежнюю общую ветку отступления. `COMBAT.WAITING` останавливает недоступную атаку; `OBSERVATION_WAIT` ждёт исправления наблюдения. Это разные причины остановки, не режимы бегства. Уведомлением об отсутствии оружия и его сбросом после перевооружения владеют actions HSM.
- Фоновое наблюдение в [monitoring.actors.ts](packages/core/src/hsm/actors/monitoring.actors.ts) публикует сырые факты `UPDATE_ENTITIES` отдельно от выбора `UPDATE_COMBAT_TARGET`; поиск маршрута не блокирует поток опасности. [selfDefense.ts](packages/core/src/utils/combat/selfDefense.ts) классифицирует все наблюдаемые виды и выбирает цель: `combatTarget` — противник для боя, `nearestThreat`/`threats` — общий источник опасности, независимый от достижимости и удержания цели. Последние позиции, краткую потерю видимости и память опасного крипера обрабатывает [threatObservation.ts](packages/core/src/hsm/utils/threatObservation.ts). Без свежего наблюдения отсутствие угроз не доказывает безопасность.
- Базовую классификацию мобов читай из `category` подключённого реестра; `type` описывает представление сущности, а не её агрессию. Исключения из категорий и видовые данные принадлежат [mobProfiles.ts](packages/core/src/utils/combat/mobProfiles.ts); условные сигналы декодируй в [mobSignals.ts](packages/core/src/utils/combat/mobSignals.ts) по именам метаданных. Неизвестные сигналы означают неопределённость, а не разрешение атаковать. Урон и изменения проходимости поступают через [worldObservation.actors.ts](packages/core/src/hsm/actors/worldObservation.actors.ts).
- Владелец памяти угроз получает все наблюдаемые сущности: подтверждение безопасности снимает прежнюю угрозу в текущем сканировании. Удержание последней позиции применяется к потере наблюдения, а не к мобу, который виден и больше не опасен. Список боевых кандидатов остаётся отдельным.
- Смерть (`ENTITY_DIED`) и потеря наблюдения (`REMOVE_ENTITY`) приходят из `core/harness.ts` раздельно. Смерть сразу снимает цель, угрозу и бюджет подхода; `deadEntities` удерживает факт для конкретного объекта до его удаления из реестра. Повторное использование серверного ID не наследует смерть. Исчезновение живого моба сохраняет краткую память угрозы и подхода. При смерти текущей цели выбирай следующую без перезапуска боя, если она доступна.
- Версия подключения выбирает реестр данных, а не разрешение на самооборону. Проверяй наличие и тип конкретного сигнала; правила известных видов и подтверждённый урон не блокируй сравнением с одной строкой версии. Для базового правила паука используй готовый `bot.time.isDay` и локальный свет; подтверждённая атака проверяется раньше освещения.
- Валидность наблюдения проверяется до фильтрации по дистанции через [spatial.ts](packages/core/src/utils/minecraft/spatial.ts). Нечисловые координаты бота или сущности инвалидируют наблюдение, не заменяют его пустым списком угроз. HSM сохраняет известные угрозы, прекращает небезопасное исполнение и ждёт корректного сканирования; восстановление координат само по себе ещё не доказывает безопасность. Recovery-обязанность при этом сохраняется. Координаты от сервера не подменяй выдуманными значениями.
- Диагностика состояния подключается в `packages/core/src/core/harness.ts` через [runtimeDiagnostics.ts](packages/core/src/hsm/utils/runtimeDiagnostics.ts). Наблюдатель только читает факты, не управляет поведением; его таймер и подписка завершаются вместе с HSM. Логируй причины и ограниченные снимки, а не полные события/сущности.
- [survival.actors.ts](packages/core/src/hsm/actors/survival.actors.ts) исполняет восстановление здоровья, безопасное питание и отход от крипера с раздельными условиями завершения. [escapeRuntime.ts](packages/core/src/utils/combat/escapeRuntime.ts) владеет одним запуском движения: сменой контроллера, пошаговым поиском альтернатив и проверкой фактического перемещения. Новые таймеры/наблюдатели внутри него не нужны: события и ticks приходят от актора.
- [escapeSafety.ts](packages/core/src/utils/combat/escapeSafety.ts) проверяет сегменты маршрута относительно всех угроз и улучшение конечной дистанции. Проверка применяется и к предварительному поиску, и к фактическому `path_update`: безопасная цель не гарантирует безопасный путь. Синхронная отмена маршрута обработчиком события должна сохраняться внутри pathfinder.
- Активный отход пересматривает оставшийся путь по текущим угрозам: безопасный путь сохраняется, опасный отменяется. `EscapeRuntime` читает массив `path_update` без мутаций; pathfinder сокращает его по мере прохождения. При обновлении зависимости проверь этот контракт физическим тестом `escapeReplanning.runtime.test.ts`. Изменение далёкой угрозы само по себе не обнуляет маршрут и прогресс.
- Критическое здоровье — инвариант всех поведений `MAIN_ACTIVITY`, включая переход из голода; его применение не перезапускает параллельный `MONITORING`. Локальная ошибка ведёт в `RETRYING`, а не освобождает обязанность выживания. Условия выхода/еды принадлежат [survival.guards.ts](packages/core/src/hsm/guards/survival.guards.ts). Небезопасность места еды после урона хранится в контексте и переживает перезапуск актора; [recoveryRelocation.ts](packages/core/src/utils/combat/recoveryRelocation.ts) откладывает построение маршрута до валидных координат. Цель откладывается, `:stop` отменяет цель, но не спасение.
- [approachPolicy.ts](packages/core/src/utils/combat/approachPolicy.ts) хранит ограниченные попытки подхода по противнику в контексте, включая краткую потерю наблюдения. [movementProgress.ts](packages/core/src/utils/combat/movementProgress.ts) — общий критерий прогресса подхода и отхода. Обновления этих обязательств размещай в [safety.actions.ts](packages/core/src/hsm/actions/safety.actions.ts); повторные одинаковые наблюдения не создают новый бюджет.
- Обновление позиции через `safety.actions.ts` снимает выполненное требование смены места еды даже вне recovery-актора; расчёт принадлежит `recoveryRelocation.ts`. Сам факт сохранённого требования не запускает движение при нормальном здоровье.
- Состояния здоровья и голода в `MONITORING` обновляют данные; приоритетами восстановления владеет `MAIN_ACTIVITY`. Повторный критический апдейт не должен пересоздавать уже работающий recovery-актор.
- После достижения безопасной дистанции ожидание регенерации использует внутреннюю границу опасности до нового отхода. Новая еда и завершение выживания требуют внешней границы; урон, потеря достоверности и повтор recovery снимают допуск к ожиданию. Эта память принадлежит recovery-актору, а не флагу владельца движения.
- Дистанции начала стрельбы и melee-сближения разделены: дальний радиус применяется только при доступном дальнем оружии и боеприпасах, не расширяет пешее преследование и безопасность отхода. `rangedAttackRange` в `context.ts` ограничивает и начало, и продолжение стрельбы; видовой follow range не является дальностью лука. Классификация, видимость и приоритет спасения сохраняются.
- Акторы и guards читают актуальную геометрию цели через [combatRange.ts](packages/core/src/utils/combat/combatRange.ts), там же задан запас дистанции возврата от меча к луку. Сохранённая `combatTarget.distance` — снимок наблюдения, не независимый источник решения. События изменения условий пересчитывают цель до выбора состояния.
- Melee и ranged начинают управление после успешной экипировки по актуальному контексту; physics ticks обновляют melee и немедленно прекращают недопустимую стрельбу. Периодический tick служит контрольной проверкой, а не задержкой первого действия. Ranged повторно проверяет цель, дистанцию, видимость и боеприпасы после `await equip`; отменённый актор не вправе атаковать, а physics callback не запускает конкурирующую экипировку.
- Наличие запасного меча в инвентаре не разрешает удар пустой рукой: потеря экипированного оружия возвращает бой через выбор состояния и повторную экипировку. Смена ranged-цели сохраняет натяжение внутри контроллера, остановка отменяет его; native-контракт описан в `patches/README.md`. Вход в отход от крипера и завершение отхода используют раздельные границы из `context.ts`; проверка завершения общая для актора и события `RETREAT_SAFE`.
- При прерывании исполнения цели текущий примитив отменяется. После восстановления `RESUMING` сначала проверяет общий бюджет цели: исчерпанный бюджет завершает цель через `IDLE`; незавершённая mining-задача возобновляется напрямую, без нового хода пилота; остальные цели идут в `TASKS.THINKING` либо `IDLE`. Не возвращайся через history в execution-состояние, чьи аргументы и ресурсы уже очищены.
- Для каждого конечного действия задай успех, ошибку и предел ожидания. Для непрерывного поведения, например следования, задай явную отмену и условия остановки. Значения лимитов читай в реализации, а не копируй из старых отчётов.
- Подписывайся на результат до запуска действия. При выходе освобождай подписки, таймеры, копание, движение и другие принадлежащие актору ресурсы. После каждого `await`, за которым идёт побочный эффект, проверяй отмену.
- Ошибки callback-сервисов публикуются через `errorEvent` в [createStatefulService.ts](packages/core/src/hsm/helpers/createStatefulService.ts), по умолчанию как `ERROR`; обработчика `invoke.onError` недостаточно. Для параллельного наблюдателя используется `THREAT_OBSERVATION_FAILED`: `ENTITIES_MONITOR.RETRYING` инвалидирует свежесть и сам перезапускает наблюдение с задержкой. Ошибка наблюдения не является ошибкой текущего лечения или задачи.
- Попытка еды в [autoEat.ts](packages/core/src/modules/plugins/autoEat.ts) имеет общий дедлайн на экипировку, употребление и восстановление предмета. Её отмена проходит до native inventory-операции через `AbortSignal`; поздний результат старой попытки не очищает новую. Ошибка/тайм-аут возвращается recovery-актору, не снимая обязанность выживания.
- Движением в каждый момент владеет один контроллер. Передачу управления согласуй с [runtimeControl.ts](packages/core/src/utils/combat/runtimeControl.ts); поздний callback старого владельца не вправе остановить или переназначить движение нового.
- Локальные повторы еды и боя принадлежат активному состоянию; лимиты локальных workflows ищи в [antiLoop.ts](packages/core/src/hsm/utils/antiLoop.ts). Бюджет всей цели принадлежит `goalExecution.ts`, а не локальным счётчикам или постоянному списку запрещённых действий.
- `WindowRuntime` владеет активными и временными окнами. Неудачное закрытие сохраняет сессию и блокирует осмотр, открытие и перенос до повторного закрытия. Закрытие подтверждается освобождением собственного `currentWindow` локально, не серверным ACK.
- Отмена/тайм-аут оконной операции освобождает вызывающий актор, но слот оконных операций остаётся занят до фактического завершения Mineflayer. Позднее открытие очищается владельцем; старый handle нельзя закрывать, если текущее окно уже другое. При неразрешившемся вызове безопасно ограничиваются только оконные операции.
- Очистка окна не завершает execution и не задерживает бой/выживание. HSM вызывает немедленную отмену/закрытие при прерывании и через корневой lifecycle-актор при `stop()`; состояние ресурса читается у владельца, а не дублируется полями или поздними событиями HSM.

### Память и внешний ввод

- Сохраняй память через `MemoryManager`, профиль — через `ProfileMemoryStore`. Новую персистентность агентских данных реализуй внутри этих модулей, а не прямыми записями `fs` из исполнителей. Изменение формата хранения требует совместимости или явной миграции и теста чтения старого формата. Активную цель не восстанавливай после рестарта без отдельного изменения контракта; персистентные задачи переживают рестарт только как `suspended` без автозапуска ([ADR-0004](.agents/adr/0004-persistent-task-records.md)).
- Текст игроков, ответы LLM и данные внешних API валидируй на границе. Инструкции внутри этих данных не являются разрешением обходить правила исполнения.

## Добавление инструмента: обязательный маршрут

1. Определи категорию: inline — информационная операция или memory API внутри хода; execution — действие через HSM; control — управление завершением хода/цели.
2. Для execution добавь определение в [executionDefinitions.ts](packages/core/src/ai/tools/executionDefinitions.ts): аргументы, схему, имя и summary. Каталог и типизированный контракт выводятся из него автоматически. Для inline/control согласуй каталог, имена и контракт в `packages/core/src/ai/tools/` и `packages/core/src/ai/contracts/`.
3. Добавь проверки допустимости и grounding в [validation.ts](packages/core/src/ai/loop/validation.ts); форму execution-аргументов проверяет parser определения. При новом источнике фактов обнови grounding.
4. Для inline подключи исполнитель через [inlineExecutor.ts](packages/core/src/ai/tools/inlineExecutor.ts). Для execution обнови `resolveExecutionInput`, guards, переходы `RESOLVE` и обработку результата в `packages/core/src/hsm/machine.ts`. Если нужен пакетный workflow, подключи его явно, как `MINING`, вместо фиктивного примитива.
5. Добавь тесты принятия и отклонения аргументов, маршрутизации, успеха, ошибки и отмены. Инструмент готов только тогда, когда путь от ответа модели до результата исполнения проверен; одной записи в каталоге недостаточно.

## Предметные проверки

Общий порядок проверки и завершения — в `AGENTS.md`. Дополнительно для затронутой подсистемы:

- Для HSM проверь повторные события, прерывание, отказ зависимости, тайм-аут и отсутствие вмешательства отменённого актора. При изменении состава состояний обнови [hsmDrawioDiagram.ts](packages/core/src/hsm/utils/hsmDrawioDiagram.ts), выполни `rtk pnpm run generate:hsm` и тест диаграммы.
- Для исправления движения проверяй перемещение, а не только вызов метода контроллера. Используй [survival.runtime.test.ts](packages/core/src/tests/hsm/survival.runtime.test.ts) как пример проверки с физикой. Непроверяемые локально условия сервера обозначай отдельно и записывай воспроизводимый ручной сценарий.

Обновляй этот файл при переносе точки входа, смене владельца или межмодульного контракта. Конкретные версии, числовые лимиты и списки всех инструментов оставляй в коде и конфигурации, чтобы правила не превращались в устаревающую копию реализации.
