# Инструкции для AI-агентов

Этот файл задаёт порядок работы в репозитории. Архитектурные правила и размещение кода определены в [ARCHITECTURE.md](ARCHITECTURE.md).

## Начало работы

1. Уточни тип запроса: объяснение, ревью и диагностика не разрешают автоматически менять код; реализация и исправление разрешают изменения в согласованной области.
2. Перед анализом кода, ревью, диагностикой или реализацией прочитай [ARCHITECTURE.md](ARCHITECTURE.md). По карте выбери подсистему, затем прочитай её реализацию, вызывающий код и тесты. Одной карты недостаточно для вывода о поведении.
3. Проверь рабочее дерево через `rtk git status --short`. Сохрани существующие изменения пользователя; не отменяй и не переформатируй несвязанные файлы.
4. До правки определи ожидаемый результат и способ проверки. Для бага сначала получи воспроизведение тестом или точным сценарием. Если неизвестный выбор меняет контракт или границы задачи, задай вопрос до реализации.

## Роли источников

- `AGENTS.md` — порядок работы агента, инструменты, ограничения и завершение задачи.
- `ARCHITECTURE.md` — карта проекта, владельцы поведения, границы модулей и правила расширения.
- Код, конфигурация и тесты — свидетельства текущей реализации. Версии, команды и значения параметров проверяй в соответствующих файлах, а поведение — по коду и проверкам.
- `docs/` — публичная документация для GitHub. Она не является эталонной архитектурой, спецификацией реализации или источником инструкций для агента. Обращайся к ней для публичного пользовательского контекста или при задаче на её обновление; технические утверждения перепроверяй по реализации.

Существующий код не отменяет архитектурные правила, а текст инструкции не доказывает, что код уже им соответствует. При расхождении обозначь факт и требуемый контракт. Исправляй нарушение в рамках задачи; если требуется изменение самого контракта или расширение области работ, согласуй его с пользователем. Внутренние отчёты агента и рабочие заметки не публикуй автоматически в `docs/`.

## Инструменты и навыки

- Shell-команды запускай через `rtk`. Для чтения и поиска используй `rtk read`, `rtk grep`, `rtk find`, `rtk ls`; для неподдерживаемых режимов — `rtk proxy`, например `rtk proxy rg --files src`. Обход RTK допустим только при подтверждённой несовместимости.
- Наличие MCP-инструментов проверяй в текущей сессии. Если доступна Serena, используй её для поиска символов и ссылок; иначе используй текстовый поиск. Упоминание инструмента в файле не означает, что он подключён.
- Проектные навыки находятся в `.agents/skills/`. При применении навыка прочитай его `SKILL.md` и обязательные ссылки до действий. Для изменения инструкций агента используй [writing-for-agents](.agents/skills/writing-for-agents/SKILL.md); указатели на предметные навыки находятся в соответствующих разделах `ARCHITECTURE.md`.
- Локальные изменения вноси через `apply_patch`. Форматирование ограничивай затронутыми файлами. Команды запуска и проверки сверяй с [package.json](package.json), требования зависимостей — с манифестами и lock-файлом.

## Ограничения действий

- Исправляй причину подтверждённого дефекта. Подавление ошибки, произвольная задержка или ослабление теста не заменяют исправление контракта.
- Не запускай `rtk pnpm run dev` или `rtk pnpm start` как обычную проверку: они подключают бота к серверу и могут менять мир. Используй изолированные тесты; живой сценарий выполняй только в согласованном окружении.
- Секреты держи в локальном окружении; для примеров используй [.env.example](.env.example). Не выводи содержимое `.env`, ключи и токены в ответы, логи или фикстуры. Перед публикацией diff проверь отсутствие секретов и runtime-данных из `data/` и `logs/`.
- Коммит, push и публикацию PR выполняй по запросу, не как автоматическое продолжение правки. Согласованные коммиты называй коротко, в императиве, с принятым префиксом вроде `feat:` или `задача:`; для PR используй [шаблон](.github/PULL_REQUEST_TEMPLATE.md).

## Проверка и завершение

- После изменения кода выполни `rtk pnpm run type-check`, `rtk pnpm run build`, `rtk pnpm run check:imports` и релевантные тесты через `rtk pnpm --filter @voxel-pilot/core exec tsx --import ./src/tests/setupEnv.mjs --test` с конкретными путями относительно `packages/core/`. Предметные сценарии проверки указаны в `ARCHITECTURE.md`.
- Для изолированных тестов ядра загружай `packages/core/src/tests/setupEnv.mjs` через `--import`: он задаёт безопасное тестовое окружение и отключает чтение локального `.env`. `rtk pnpm test` включает этот preload, все тесты ядра и проверки workspaces.
- После изменения только инструкций проверь ссылки, существование путей, противоречия и сохранение правил. Runtime-тесты для такой правки не требуются.
- Проверь итоговый diff: только согласованные изменения, без случайных артефактов. Публичные материалы обновляй, когда задача меняет описанное в них поведение; внутренние инструкции поддерживай в файле-владельце правила, без копий.
- В завершении назови результат, изменённый контракт, выполненные проверки и ограничения. Если проверка не выполнена, укажи это явно. Для серверного бага без live-проверки дай воспроизводимый ручной сценарий в сводке; не объявляй его проверенным по unit-тестам.
